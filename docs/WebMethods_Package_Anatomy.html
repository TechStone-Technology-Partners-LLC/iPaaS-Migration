WebMethods Package Anatomy

A visual walkthrough of one real package — GLDFundingEngine20080714 — from the files on disk, through the deterministic call-graph survey and classification, to a payment's journey through the pipeline, and finally the three representations: raw XML → extracted IR → analysis document.

1The package on disk

A webMethods package is a folder of services. Six of them here contain logic (a flow.xml each); the rest are schemas, document types, and manifests.

3Classification — rules applied to graph facts

"Classify" means: for each flow, combine two deterministic facts — who calls it (in-degree) and is it exposed (manifest + registration) — and a role falls out.

FlowCalled byExposed?→ RoleDeterministic?
registerFlowServiceForSOAP—manifest startupInfrastructure✅ fully

processFundingRequestthe wrappernoHelper — the business core✅ facts · ⚖ recipe decision
processACHBatchnobodynot registeredENTRY POINT, presumed scheduled⚖ + S-list item
processACHBatch_venkatnobodynoDead — dev copy⚖ evidence-supported

The judgment residue (⚖) is small and lands in three specific places:

  1. The wrapper decision: the graph says the exposed unit is wrapper → engine, two flows. The recipe decision is one recipe — because the wrapper's whole job (SOAP envelope parsing, request/response logging) is what a Workato callable trigger does natively. The wrapper dissolves into the trigger.
  2. The invisible trigger: processACHBatch has no caller and no registration — the graph proves something external fires it, but the schedule lives in server config outside the package. Only an SME can supply it → S-list.
  3. The dead copy: _venkat is uncalled, unexposed, and calls a strict subset of the real batch flow. Rule-flagged as dead; human confirms at the gate.
The package map — what the survey hands to the pipeline 2 entry points → 2 recipe pipelines (FundingRequest = wrapper+engine merged; ACHBatch) · 1 dead flow classified, not migrated · 3 external boundaries → the connection registry · 2 S-list flags (batch schedule; confirm what the registration exposes). A human confirms this half-page in minutes — then each entry point runs the full analyze → test → gate → build pipeline independently.

The one rule that prevents "two truths" confusion The raw file is authoritative; the IR is a derived index of it. The agent works from the IR (small, clean, in context) and opens the raw file only where the IR's residue list points, or where something looks odd. If IR and raw ever disagree, that's not ambiguity — it's a detected extractor bug, reported in the discrepancy list. A map with grid references into the territory; the territory always wins.

The pattern to carry to bigger packages: extraction gives facts, classification applies rules to facts (~80% mechanical), and the judgment residue is small, specific, and always lands in an artifact that already has an owner — the analysis doc, the S-list, or the human gate. On a 40-service package the tables get longer; the split stays the same.
